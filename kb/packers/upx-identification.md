# UPX 壳识别

## 摘要

用于快速判断 PE 样本是否经过 UPX 或 UPX 风格压缩处理，并决定是直接脱壳还是继续核验是否存在二次改造。

## 适用场景

- 保护类型：轻量压缩壳、常见 CTF 壳、经修改的 UPX 变种。
- 文件类型：Windows PE32 / PE32+。
- 分析目标：判断是否值得优先执行“现成脱壳 -> 核验 OEP -> 校验导入”路径。
- 不适用条件：重虚拟化保护、Themida/VMProtect 类复杂保护、内核驱动。

## 识别信号

- 节区名接近 `UPX0`、`UPX1`，或呈现少量大节区配合高熵内容。
- 入口点附近是短跳、解压 stub、寄存器保存恢复和内存拷贝逻辑。
- 导入表非常稀疏，但运行后 API 使用迅速增多。
- 文件头看起来正常，但静态字符串很少、代码段体积明显偏小。

## 判断依据

- 节区命名只是弱证据，改名后仍可能是 UPX 风格 stub。
- 真正的强证据通常来自入口附近解压逻辑、内存写入模式和运行后映像变化。
- 若脱壳工具报告成功但产物无法正常分析，优先怀疑“原作者对 stub 做过二次修改”。

## 处理思路

1. 先做轻量识别：节区、入口、导入稀疏度、字符串分布。
2. 若强烈像标准 UPX，优先尝试标准脱壳路径。
3. 脱壳后核验：入口是否回到正常函数序言、导入表是否可解析、代码体量是否恢复。
4. 若标准路径失败，转向调试器观察解压后的内存映像，再决定是否手工 dump。

## 常见误区

- 把节区名 `UPX0/UPX1` 当成充分条件。
- 脱壳成功后不核验 OEP 和导入表，直接开始逆向。
- 看到字符串恢复就认为已经完成脱壳，忽略仍然存在的运行时修复逻辑。

## 失败信号与转向条件

- 标准脱壳后程序损坏或无法运行。
- 入口仍位于明显的 stub 中，而不是业务逻辑附近。
- 导入表缺失严重，需要转向内存 dump 和导入重建流程。

## 工具与脚本

- 工具：PE 头查看器、静态反汇编器、调试器、内存 dump 工具。
- 现有脚本：无固定脚本，优先记录样本的节区、入口和导入差异。
- 输出产物：脱壳前后 hash、节区对比、入口截图或地址记录。

## 记录规范

- 样本 hash：必须记录原始样本与脱壳产物。
- 平台与位数：x86 / x64。
- 是否需要管理员权限：通常不需要。
- 是否涉及驱动、服务或内核组件：通常否。
